# Site Response Bot

Сервис круглосуточно проверяет доступность заданных сайтов, фиксирует сбои в PostgreSQL и отправляет групповые уведомления в Bitrix24 через webhook.

## Возможности

- Проверяет все сайты каждые 30 секунд.
- Считает сайт доступным только при HTTP-ответе `200`.
- Преобразует сетевые ошибки, проблемы SSL и таймауты во внутренние коды `900–903`; непредвиденные ошибки получают код `999`.
- Открывает инцидент при первой ошибке, но не отправляет уведомление.
- Подтверждает инцидент при второй подряд ошибке.
- Объединяет подтверждённые проблемы нескольких сайтов в одно сообщение.
- Фиксирует смену кода во время подтверждения, например `502 → 503`.
- Объединяет восстановления сайтов в одно сообщение и указывает, какие сайты всё ещё недоступны.
- Не отправляет оперативные уведомления с 18:00 до 08:00 по Москве.
- Отправляет одну утреннюю сводку после 08:00 за период с 18:00 предыдущего дня.
- Не дублирует утренний отчёт после перезапуска контейнера.

## Как работает проверка

1. При запуске сервис добавляет заданные сайты в базу данных.
2. Каждые 30 секунд выполняются параллельные HTTP GET-запросы ко всем сайтам с таймаутом 15 секунд.
3. Новый статус сравнивается с предыдущим состоянием сайта.
4. Для ошибок и восстановлений создаются или обновляются инциденты.
5. Днём сервис отправляет пакетные уведомления о подтверждённых сбоях и восстановлениях.
6. После 08:00 сервис отправляет ночную сводку, если она ещё не была отправлена в текущий день.

## Правила инцидентов

| Состояние | Действие |
| --- | --- |
| `200 → ошибка` | Открыть инцидент и дождаться повторной проверки. |
| `ошибка → ошибка` | Подтвердить инцидент; днём добавить его в пакетное уведомление. |
| `ошибка → 200` | Закрыть инцидент; если о нём сообщали, добавить сайт в пакетное сообщение о восстановлении. |
| `200 → 200` | Обновить время последней успешной проверки. |

Если первая и повторная ошибки имеют разные коды, в сообщении будут указаны оба результата.

## Ночной период и утренний отчёт

Ночной период длится с 18:00 до 08:00 в часовом поясе `Europe/Moscow`.

В это время сервис продолжает проверять сайты и сохранять инциденты, но не отправляет оперативные сообщения. После 08:00 формируется одна сводка со всеми проблемами периода:

- временем первой ошибки;
- кодом и описанием ответа;
- изменением кода при повторной проверке, если оно было;
- временем восстановления либо отметкой, что сайт всё ещё недоступен.

Если проблем не было, отчёт сообщает, что все сайты были доступны.

## Структура базы данных

- `links` — список сайтов, последний статус и времена проверок.
- `site_incidents` — история инцидентов: первая и повторная ошибки, время восстановления и состояние уведомлений.
- `daily_reports` — даты уже отправленных утренних сводок.

Все даты в базе хранятся как Unix timestamp; отображение в сообщениях выполняется по московскому времени.

## Конфигурация

Создайте файл `.env` в корне проекта:

```env
DB_HOST=db
DB_PORT=5432
DB_USER=postgres
DB_PASS=postgres
DB_NAME=app
WEBHOOK_URL=https://<ваш-bitrix24-webhook>
LOG_LEVEL=INFO
```

Для подробной диагностики установите `LOG_LEVEL=DEBUG`.

## Запуск в Docker

```powershell
docker compose up -d --build
```

Docker Compose запускает PostgreSQL, ждёт его готовности, применяет Alembic-миграции и запускает сервис.

Остановить сервис:

```powershell
docker compose down
```

## Логи

Просмотр логов приложения:

```powershell
docker compose logs -f app
```

Уровни логирования:

- `INFO` — запуск, выполнение проверок, смены состояний и отправка отчётов;
- `WARNING` — ошибки сайтов, webhook, SSL и таймауты;
- `ERROR` — сообщение не удалось отправить после трёх попыток;
- `DEBUG` — подробности HTTP-запросов и обновлений БД;
- `EXCEPTION` — непредвиденные ошибки с traceback.
